# Foundation conventions

Requirements authority: root Plan.md, Module.md, Prototype.md, Database.md. Review and backlog: [foundation-review.md](foundation-review.md).

Use one modular Laravel monolith. `app/Actions/{Domain}` owns business transactions; `app/Services` owns reusable domain/infrastructure work; `app/Policies` combines permission/scope/ownership; `app/Http/Requests` validates HTTP boundaries; `app/Livewire/{Admin,Rider,Account}` orchestrates server-rendered interactions. Components call actions/services rather than embedding workflow logic in views or routes. Introduce domain subdirectories as functionality arrives, without an empty class for every future table.

`resources/views/layouts` provides Admin and Rider shells; `components` contains shared design-system inputs/buttons/feedback; `livewire` contains screen views. Alpine comes from Livewire; do not install a second runtime. Tailwind 4 uses CSS-first configuration and locally available system fonts.

`database/migrations` contains executable, dependency-ordered foundation DDL and exact package-owned migrations (Spatie/Pulse). `database/seeders` has reference/permission bundles without accounts; the explicitly invoked BrowserTestSeeder is restricted to isolated `*_e2e` local/test databases. Models use bigint primary keys and generated UUID v7 public route keys; public IDs never substitute for policies. All business timestamps are UTC/timestamptz. Names and contacts remain encrypted when introduced; no plaintext searchable PII schema is added by convenience.

Foundation tables: reference_values, staff, users, clients, user_client_scopes, audit_logs, outbox_events, processed_events, notifications; Spatie roles/permissions/three pivots; framework reset tokens/failed_jobs/job_batches; Pulse package tables. M13 adds debtors, contacts, addresses, customer_categories and customer_category_assignments with same-client constraints and preserved history. See Database.md's catalogue for future account/property/party/batch/import dependencies and [customer-management.md](customer-management.md) for the implemented boundaries.

M10 personnel reuses `staff` and `users.staff_id` without new schema. `SaveStaff` owns validated personnel writes; `InviteStaffAccount` owns explicit, separately authorized account provisioning. Employment position, Rider eligibility and login role are independent. Personnel managers require active `admin.access` plus `riders.manage`; personnel is organization-wide because the documented schema has no staff/client membership. This permission exposes no customer or task portfolio data. `users.invite` is reserved, and Admin invitations also require `roles.manage`.

Staff edits take a transaction-scoped PostgreSQL availability advisory lock followed by a staff row lock. A revision derived from persisted attributes and the latest staff audit ID rejects stale and same-second ABA edits without adding an undocumented version column. Availability reductions require a reason, refuse self-removal and check unreleased allocations on nonterminal tasks when M05 tables exist. M05 allocation writes must lock/recheck staff availability before assigning. Partially installed task tables fail closed. No staff deletion or account-role mutation is introduced.

Invitation tokens are broker-hashed, throttled and single-use. Reissue preserves the selected account bundle and refuses active identities or direct-permission changes. Contact changes invalidate pending invitations; activation checks that the invited identity still matches its active staff email. Notification dispatch runs after commit and reports preparation, transport acceptance or failure accurately; array transport stays local and any log transport chain is blocked. Mail errors leave an invited identity recoverable by authorized reissue. Application audit/log records exclude tokens and raw mail exceptions.

AuditWriter accepts only redacted metadata keys. Sensitive actions append audit in the same PostgreSQL transaction. AuditLog rejects mutation and PostgreSQL rejects direct update/delete; production runtime roles must additionally lack schema/TRUNCATE/audit update/delete rights. Use a separate migrator. Outbox persistence/dedupe tables are present; real dispatch and reconciliation handlers ship with the first queued business module, not a fictitious catch-all handler that drops unknown events.

`CustomerOverview` supplies the read-only customer dashboard using the same permission and effective client subqueries as customer management. PostgreSQL aggregates count records and group the seven-day creation chart in the configured business timezone; latest records/events are bounded and scoped. No task, financial, attendance or assignment KPI is inferred from customer counts. Shared Blade design components and centralized CSS provide the InteXcode presentation independently of business actions.

M03 batch metadata uses `assignment_batches`/`AssignmentBatch`, `SaveAssignmentBatch`, `ChangeBatchStatus` and `AssignmentBatchPolicy`. Shared time-bound client query logic now lives in `Services/ClientAccess`; customers and batches both use it without duplicating portfolio rules. Client locks precede batch row locks; optimistic `lock_version` rejects stale metadata/status writes. Client identity is immutable in application validation and a PostgreSQL trigger. The seven documented assignment types and fourteen states reuse reference_values and composite foreign keys. Client/external-reference uniqueness includes archives; blank references normalize to null.

Batch creation always starts active. Archival is a separate reasoned, confirmed action that checks disposition and retains history; archived metadata cannot be edited. Reopening additionally requires reserved `assignments.reopen`, which is not silently granted to existing users or ordinary Admin bundles. Type changes are blocked once task/import history exists, preventing historical work from being reinterpreted under another assignment variant. M04 import and M05 manual task/account screens are now implemented as described below; reporting and legacy task import adapters retain their dependency gates.

M04/M05 writers lock the client then parent batch and recheck active status before intake/task writes. `BatchWork` reads canonical child tables only when present. Archival blocks nonterminal tasks, completed tasks lacking approved review, nonterminal imports and unreconciled accepted import rows. The implemented import/task writers now share that parent-lock contract; remaining adapters must preserve it. Sensitive metadata is excluded from audit payloads; changes record field names/status and required transition reason in the same transaction.

Redis queues use `after_commit` and retry_after=180 seconds; workers must time out earlier (120 seconds suggested). Dedicated queues are default/imports/exports/email/whatsapp/webhooks/media. Local Sail uses one durable noeviction Redis service. Production must separate queue and cache services/policies. Private S3 is configured without credentials; quarantine/scanning/authorization and document metadata arrive before enabling uploads.

Pulse routes require authenticated, active users and monitoring.view even locally. Recording is disabled pending privacy/retention review. Sentry has no DSN by default and sends only a minimal sanitized incident signal if enabled; request/exception/body/SQL/breadcrumb data are withheld. CloudWatch infrastructure logging and AWS IAM/region/domain/provider activation belong to the deployment phase. Application logs remain restricted and must not receive raw customer payloads in later modules.

GitHub is canonical; GitLab is a read-only mirror. The CI template runs only protected refs and verifies its SHA against the configured protected GitHub main branch. Set GITHUB_CANONICAL_REPOSITORY as a protected trusted URL and require GitHub reviews/branch protection before activation. No remote URL, token, mirror, deployment or branch protection was provisioned by this increment. Production image digests, static analysis, container scanning, signing, AWS OIDC and deploy/approval jobs remain Phase 7/launch work. CI itself remains unexecuted until a runner/mirror is configured.

M04 now implements UI14/UI15/UI39/UI57/UI58 against the eight canonical registry/staging/document tables, with existing outbox/processed-event/notification storage. Customer and Batch contracts call the existing M13/M03 writers under the same client-first lock order. Preview uses a rolled-back savepoint, producing no committed target or audit records; queue processing commits each target, row disposition and reconciliation count atomically. Failed/processed rows are not conflated with rejected/duplicate input rows. A clean scan, reviewed mapping and exact preview confirmation are required, and target revisions are rechecked at commit.

Private S3 source objects and row payloads are encrypted; only bounded masked samples and redacted field/error codes reach review/error downloads. ClamAV INSTREAM fails closed. XLSX archive and XLS OLE/BIFF safety checks precede the validated parser; formulas are never evaluated. Optional Sail profile `imports` supplies ClamAV without publishing a host port. Native S3/Redis/ClamAV integration and Docker boot remain unverified; local preview never marks a source clean to work around missing services. The initial two system-seeded template contracts have no invented creator identity; administrator-created versions record their actor.

`imports:dispatch` publishes only known M04 outbox events, acknowledges publication after queue handoff and retains failed publications for retry. Worker checkpoints and row locks make at-least-once deliveries safe. Interrupted jobs preserve processed records and reconcile remaining accepted rows as failures. Re-uploading a failed frozen attempt starts a separate reviewed attempt; retries retain the original mapping and revisions. Refer to README for service commands, explicit limits and available contract fields. Account/task/payment/databank kinds remain unavailable until their required modules and source contracts exist.

M05 extends the same action/service/policy structure with SaveDebtAccount, SaveTask, TaskOperation, TaskAccess and TaskHistory. It reuses Debtor and Staff rather than introducing Customer/Rider duplicates. Client/account/property/party FK constraints protect namespace consistency; task source identity and append-only task history are immutable. Account edits preserve prior party observations and use a fingerprint revision; task metadata and operation selection use lock_version. Effective relationship checks retain microseconds and use PostgreSQL statement time, allowing valid records created in the same transaction without weakening expiry checks.

UI55/UI56/UI19/UI16–18 use centralized DebtOps components, responsive monitoring cards/tables and scoped selectors. The M05 outbox consumer uses only tasks.operation events on the default queue. tasks:dispatch acknowledges queue handoff, retries publication failures and never reports queue acceptance as applied work. Replays preserve applied items, interrupted jobs reconcile remaining items, and stale/ineligible items fail without overwriting another change. Receiving Rider access is rechecked at execution. Current task allocation is unique in PostgreSQL; previous allocations are released rather than deleted. M06/M07 own future visit/checklist/review state transitions and cannot be simulated by an Admin status dropdown.


M06 adds RiderAccess, RiderWork, CompletionChecklist and TaskProof, reusing Task, CollectionActivity, PropertyInspection, FollowUp, Document and immutable submission/manifest records. Actions lock client → batch → task, recheck allocation/eligibility/grants/scope and preserve optimistic versions plus history. Completion digests pin saved policy/visit/business/remarks/lookup labels/proof; there is no Rider approval endpoint.

Approved M06 policies are reference master data; missing/malformed policies block use. Backdating is bounded by MYT calendar dates, audited and retains encrypted reason/original entry timestamp. New visits are immutable versions with exact activity-linked proof. Scans use only tasks.proof_scan durable outbox events, the media queue and at-least-once checkpoints. Private S3 bytes are encrypted and hash checked. Sanitized evidence is immutable once submitted. Former assignees receive only redacted own receipts. Admin task detail/customer visits use task policy and scope. Visited/Pending Completion derive from recorded visits on in-progress work. M07 review decisions and legacy-only TaskObservation mappings remain separate.


M07 adds TaskSubmissionPolicy, SubmissionEvidence and ReviewSubmission. Review reads the encrypted immutable completion snapshot and pinned labels/policy, not current editable master data. Scoped records are locked in deterministic client/batch/task/submission order. TaskReview uniquely identifies a submission/cycle, forbids self-review and is append-only in PostgreSQL; remarks are encrypted. Task projection, completion time, history, redacted audit and database-only Rider notification share a transaction.

Exact bulk selection is bounded at 50 and signed for 20 minutes. Each row is reauthorized and version-checked. Any failure rolls back all new decisions and reports the affected references; same-review retries reuse existing receipts. Earlier cycles remain immutable and later reviews link back through supersedes_review_id. M07 does not reuse a payment marker as a completion decision, activate an external channel, or infer DRMS bulk/range semantics.

M10 attendance follows Plan.md#plan-attendance, Module.md#m10-approved-policy, UI33/UI53/UI59 and Database.md's four attendance tables. `ConfigureAttendance` publishes immutable typed policies and bounded explicit staff/date calendar assignments. A per-policy advisory transaction lock serializes version publication; staff locks serialize assignments/punches/corrections. `ClockAttendance` accepts no caller-supplied punch times, uses UUID replay and locks the existing staff row; PostgreSQL enforces one effective open interval and one punch per schedule/unscheduled service day. `AttendanceStatus` calculates only from pinned rules and effective intervals, subtracting the pinned fixed break exactly once. UTC storage and MYT service dates remain distinct; overnight clock-out stays on the scheduled start date.

`CorrectAttendance` compares canonical typed snapshots under staff/target locks, forbids requester/owner approval and retains raw events. Planned-shift/calendar changes and effective time corrections require a separate decision; unchanged rules stay pinned. The projection, immutable reviewed request, redacted audit and safe database notice share a transaction. Missed raw clock-out stays null after an approved effective closure. `AttendanceRegister` unions authorized calendar expectations with unlinked punches, derives absence only after scheduled end and keeps pending corrections as an overlay. Personnel access stays organization-wide, but Admin attendance requires current shared active client scopes; own history has no customer data. A single materialized query provides bounded CSV/print snapshots without a new PDF dependency. No payroll, guessed holiday calendar or new identity/evidence entity exists.

M11 Call Centre follows Plan.md#plan-communication, Module.md M11, UI60/UI64 and existing debtors/contacts/collection_activities/follow_ups. `CallAccess` provides current-client customer search and permitted call/visit history; `RecordCall` locks client/customer, rechecks active grants, validates optional task/contact context, freezes encrypted outgoing/manual context, and atomically writes any required reminder and redacted audit. Request UUID replay cannot duplicate a call or reminder and rechecks current access. The owner-approved historical window is today/yesterday in MYT with a reason, never a future time; original server entry time is retained.

`SaveCustomerContacts` shares the original customer contact validator/persistence service, requires its separate contact permission and compares the customer revision. Changes append/supersede observations rather than overwriting history. `ResolveFollowUp` accepts only assigned-agent pending call reminders with a matching version and required resolution remarks. PostgreSQL prevents reminder context changes, reassignment, deletion and rewritten terminal decisions. Existing Rider reminders remain in their source workflow. Reference metadata separates call-only outcomes from visit validation and selectors while preserving shared Promise to Pay. No new call/customer/Rider entities, financial posting, provider activation or external messages are introduced. Real channel history and telephony follow M14; legacy databank remains G05-gated.
